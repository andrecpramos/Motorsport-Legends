## Start here, in this order

1. **[ASSESSMENT.md](ASSESSMENT.md)** — the readiness verdict for this project, and the gaps in the
   order they are worth closing. If it found a critical gap, that gap outranks everything else on
   this list. Configuring tooling on top of a project with no verification capacity does not
   produce a well-founded setup, it produces a well-documented one.

2. **[AGENTS.md](../AGENTS.md).** Delete every rule you would not actually enforce in review. A
   diluted instruction file is worse than a short one, because agents weigh all of it equally and
   you stop being able to predict which rule was applied.

2. **[docs/adr/0002-project-invariants.md](adr/0002-project-invariants.md).** Each invariant needs
   its "why", its "what breaks it", and the test that pins it. The middle one does the most work:
   naming the tempting mistake specifically is what stops it being made.

3. **Search the tree for `TODO(setup)`.** Every one marks a decision the wizard could not make for
   you. Some are genuinely optional. The ones in the governance policy and the runbook are not.

4. **Run `dev.bat check`.** If it does not pass on a clean checkout, fix that
   before anything else — it is what every other instruction in this foundation assumes works, and
   it is what an agent will run when asked to verify a change.

5. **Run the checks.**
   - `node tools/doc-drift.mjs` — it will list every unfilled placeholder, which is the fastest way
     to see the remaining work.
   - `node tools/release-risk.mjs` — score a real diff and see whether the hot-path table matches
     your instincts about this codebase.

## The four things worth understanding

Everything above follows from these, and if the documents ever disagree with them, trust these.

1. **AI relocates work from authoring to verification; it does not remove it.** Throughput and
   stability move in opposite directions because generation outpaces review and testing. The
   pipeline is the constraint, not the assistant.

2. **A test that raises coverage while asserting nothing is worse than no test**, because the
   number is now lying to you. Mutation testing is how you tell which kind you have.

3. **An agent with credentials turns prompt injection into a supply-chain problem.** Blast radius
   is a property of your configuration, not of the attacker's skill. Draw the line at side effects,
   not at intelligence.

4. **Instruction files are a record of corrections, not a style guide.** Their value comes entirely
   from being added to when something goes wrong. The first entry you write yourself will be worth
   more than everything generated here.

## Re-running the wizard

Safe at any time. Nothing you have edited is overwritten without being asked.

```bash
node starter-kit/setup.mjs --only=security   # redo one phase
node starter-kit/setup.mjs --dry-run         # see what would change
```

Your answers are stored in `.sdlc-kit.json`, which is also read at runtime by the checks — the
hot-path table in particular. Editing that file directly is expected, and updating it after a
postmortem is the habit that makes the risk score worth having.
